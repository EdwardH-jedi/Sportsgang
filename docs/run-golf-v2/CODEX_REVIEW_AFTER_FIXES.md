## Confirmed findings

### R1 — P1: blocking leaves the existing contact channel active

**References:** `apps/mobile/src/screens/explore/PartnerDetailScreen.tsx:124`; `apps/api/app/services/chat.py:15–22,32,65`; `apps/api/app/services/matches.py:43–55`; `apps/api/app/routers/chat.py:108–115`; `apps/api/app/services/bookings.py:108–117`.

**Trigger / expected:** match two users, block either participant, then access the existing match directly. The confirmation promises the blocked user cannot message the blocker. Supported contact must be denied bilaterally by server authority.

**Actual / impact:** on real migrated PG, block returns 201, both users' message POST returns **201**, both message GETs return **200**, both match lists retain the active match, and the blocked user can propose another booking (**201**). Discovery exclusion works in both directions. A user can continue receiving unwanted contact after being told they are protected. HTTP is reproduced; WebSocket's participant-only admission/broadcast path is a source-confirmed missing boundary, not a fresh socket reproduction.

**Evidence:** [api-probe.json](independent-evidence/api-probe.json), [api_probe.py](independent-evidence/api_probe.py), native block confirmation capture. The server omission predates this branch; the new Block action makes an explicit false promise and exposes it in this flow.

**Smallest repair:** one bilateral interaction authorization boundary reused by match/contact reads, message writes, socket admission/delivery, discovery actions and new proposals. Define retained booking/history access separately so a contact restriction does not destroy audit data. Do not fix this by changing copy alone.

**Required coverage:** block in either direction on an existing match; direct GET/POST bypass; new interest/proposal attempts; block concurrent with like/send; already connected sockets after block; deleted/inactive participants; unblock restores only supported access. No post-block unauthorized persisted message or delivered notification.

### R2 — P1: QA stop commands do not establish process or worktree ownership

**References:** `scripts/qa/qa.py:52,230–239,254–269,289–296,559–578`; `scripts/qa/compose.qa.yml:8`.

**Trigger / expected:** stale state points to a reused PID, or another worktree uses the launcher. Stop/down/restart must act only on resources provably owned by this QA instance.

**Actual / impact:** `proc_alive` checks only live PID plus a port substring. It ignores recorded cwd, command and start time before signaling the entire process group. A sacrificial Python process in the temporary directory, with only `--port 8130` in its arguments and forged metadata claiming the API worktree, was accepted and terminated. No real service PID was used. Every worktree also controls the same hardcoded `sportsgang-qa` project / database / volume, while state and generated credentials are worktree-local. `down` can stop shared containers without possessing their process state. This risks interruption or destructive reset of another tester's stack.

**Evidence:** [qa-probe.json](independent-evidence/qa-probe.json), [qa_probe.py](independent-evidence/qa_probe.py). Cross-worktree destructive commands were not exercised against the human stack.

**Smallest repair:** explicit canonical QA instance ownership, fail-closed process identity (resolved cwd, executable/arguments, process start identity and expected process group), and a resource namespace/lock strategy. For intentionally shared QA, one owner must control lifecycle and other worktrees must refuse conflicting config or destructive commands. Preserve the current named volume during adoption.

**Required coverage:** reused PID, same port marker in unrelated argv including prefix ports, foreign cwd/start identity, cross-worktree state/config conflict, port collisions, restart/down/reset against two disposable instances, no unrelated group signals, startup failure after partial resource creation.

### R3 — P2: a late Booking Detail response displays A while actions target B

**References:** `apps/mobile/src/screens/bookings/BookingDetailScreen.tsx:85–100,102–114`.

**Trigger / expected:** hold booking A's fetch, change the same screen's route to B, resolve B, then resolve A. Only the current route/account may update detail and action state.

**Actual / impact:** the screen displays Partner A after B loaded, but Cancel posts to **`/bookings/B/cancel`**. The new retry callback has no generation/owner/unmount guard. It can cancel a different commitment from the one visible. The missing guard existed before the home retry refactor and persists through it.

**Evidence:** [codex-review-booking.test.tsx](independent-evidence/codex-review-booking.test.tsx), [independent-mobile-final.log](independent-evidence/independent-mobile-final.log). Actual screen code, controlled deferred transport. Initial offline/retry and route-B error controls pass; no claim that an ordinary B error leaks A.

**Smallest repair:** bind fetch and transitions to current booking ID, account and request generation; invalidate on route/owner change and unmount; guard success, failure and finally; never render/action a booking belonging to a different binding.

**Required coverage:** A/B responses in both orders, old rejection/finally, repeated retry, old transition completion, logout/replacement, unmount, not-found and 403. Visible detail ID and transition ID must always match.

### R6 — P2, pre-existing: audit timestamps have no timezone contract on the wire

**References:** `apps/api/app/models/chat.py:20`; `apps/api/app/models/booking.py:36–37`; `apps/api/app/schemas/chat.py:18`; `packages/shared-types/src/common.ts:23`; `apps/mobile/src/lib/api.ts:28–40`; `apps/mobile/src/lib/messages.ts:66–80`; `apps/mobile/src/screens/safety/BlockedUsersScreen.tsx:205–214`; `apps/mobile/src/screens/chat/ChatScreen.tsx:345–350`.

**Trace / actual:** migrated columns for messages, booking audit dates, blocks, reports, notifications, push tokens, calendar syncs and Google token connection date are `timestamp without time zone` with `now()` defaults. Inferred ORM datetime remains naive, Pydantic serializes without suffix, shared `ISODateString` is only a string alias, and mobile key transformation does not normalize values. Real GET messages returned `2026-10-02T15:30:00` after a controlled local fixture write.

At the same transaction instant, `now()::timestamp` under PostgreSQL UTC versus Sydney sessions differs by ten hours. Therefore local UTC settings do **not** establish historical production provenance, and setting only the API process TZ is insufficient.

**Visible impact:** using the actual `formatPreviewTimestamp`, UTC parses the fixture at 15:30Z and renders 3:30 PM. Sydney parses it at **05:30Z**, showing “Oct 2” where the aware instant should show **1:30 AM on Oct 3**. Blocked Users likewise shows Oct 2 instead of Oct 3. The confirmed visible consumers are chat-list previews and blocked dates; other listed columns establish contract risk, not eight independently broken screens. Booking appointment bounds remain aware and correctly displayed.

**Ordering:** Chat merges message/booking audit strings lexically. Uniform offsetless values from one stable DB timezone preserve their relative order, so this review does **not** claim a current uniform-data timeline inversion. Mixing timezone representations or historical session zones during a partial repair can break chronology; all compared sources need one instant contract and deterministic ties.

**Evidence:** [api-probe.json](independent-evidence/api-probe.json), [timestamp-utc.json](independent-evidence/timestamp-utc.json), [timestamp-sydney.json](independent-evidence/timestamp-sydney.json), [timestamp.js](independent-evidence/timestamp.js). Schema/model/formatter behavior exists in main; no production historical data was inspected or rewritten.

**Smallest coherent repair:** first establish deployed schema/session-TZ provenance. If the legacy values have one documented zone, normalize all relevant responses centrally to aware ISO instants and guarantee the same future-write convention; this can precede a column migration. Otherwise define aware future writes plus an explicit legacy adapter/provenance policy. A blind historical `AT TIME ZONE 'UTC'` rewrite is not justified. Migrate columns only with established assumptions and a reversible plan; normalize message and booking audit dates together.

**Required coverage:** UTC/Sydney API **and DB session** zones, midnight/DST boundaries, legacy rows, optional/null values, preview and block rendering, mixed message/proposal chronology, equal-instant offsets and stable ID ties. Keep F5 appointment bounds independent.

### R7 — P2: Retry removes the stale-data warning before recovery

**References:** `apps/mobile/src/hooks/usePlans.ts:386`; `apps/mobile/src/screens/plans/MyPlansScreen.tsx:133–135`.

**Trigger / expected:** load a confirmed row, fail its source on refresh, press Retry and hold the new response. Retained data must stay labeled stale until the corresponding source recovers.

**Actual / impact:** retry eagerly sets `error:null`; the notice disappears while old rows remain and the request is unresolved. Rejection restores it later. The home notice otherwise correctly distinguishes first-load and refresh failures. This can imply freshness during slow or stalled retries.

**Evidence:** [codex-review-plans.test.tsx](independent-evidence/codex-review-plans.test.tsx). Native source failures and eventual recovery independently pass; the pending-interval defect uses a controlled deferred response.

**Smallest repair:** preserve source error/freshness during retry, clear only on successful replacement, and expose retry progress/disable repeated retry without hiding the warning.

**Required coverage:** held retry, repeated taps, one/both sources, successful zero-row load then failed refresh, partial recovery, failure after retry, and obsolete generations.
