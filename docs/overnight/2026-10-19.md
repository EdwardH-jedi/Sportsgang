### S11 — failure-safe photo replacement (PR #24)
- Bug: `PUT /users/me/photos` deleted the rows and the user's media directory *before* writing the uploads. Now: empty uploads → 422 before anything is touched; new files are written beside the old ones (names are unique); rows and `avatar_url` swap in one transaction; the replaced rows' files are deleted only after the commit.
- Codex took several rounds. R1: the rollback expired the session-bound `current_user` (`MissingGreenlet`), and the cleanup swept a concurrent replace's staged files. R2: an ambiguous commit (connection lost after PostgreSQL committed) would delete files that committed rows point at, and the row lock had no PostgreSQL test. R3: the post-commit `refresh()` could find its rows already deleted by a newer replace, turning a successful replace into a 500 (the same pattern was on `main`). Fixes: the user id is read once up front; cleanup is limited to the replaced rows under `SELECT … FOR UPDATE` on the profile; SQL runs in an explicit `flush()` (failure → roll back and remove the new files), while a failing `commit()` keeps the new files; the response is snapshotted inside the locked transaction; a new PostgreSQL test runs two concurrent replaces. R4: APPROVE.
- The PG test first passed even without the lock, because the second request was still opening a pool connection while the first finished. It now warms two connections first: 5/5 pass with the lock, 3/3 fail without it (`UniqueViolation` on `uq_profile_photos_profile_position`).
- +7 unit tests (713), +1 integration test. Each fix's test failed before that fix.

### S12 — chat WebSocket reconnect (PR #25)
